# Геометрические паттерны на основе астральных аспектов

Документ описывает идею генератора визуальных паттернов, который превращает астрологическую картину момента (планеты + аспекты между ними) в геометрические образы. Конечная цель — отдельная веб-библиотека, пригодная для использования вне основного проекта.

---

## Часть 1. Семейства паттернов

Все семейства разделяют общий вход: набор планет с эклиптическими долготами и набор аспектов между ними с фактическим орбисом и силой. Различаются только правила перевода аспектов в геометрию.

### 1.1. Звёздные многоугольники {n/k}

Делим окружность на `n` равноотстоящих точек (естественный выбор — 12 по знакам зодиака, 36 для деканов, 72 для пятиградусных секторов). Каждый тип аспекта задаёт шаг `k`:

| Аспект      | Угол | Шаг при n=12 | Имя {n/k} |
|-------------|------|--------------|-----------|
| Соединение  | 0°   | —            | —         |
| Секстиль    | 60°  | 2            | {12/2}    |
| Квадрат     | 90°  | 3            | {12/3}    |
| Трин        | 120° | 4            | {12/4}    |
| Квинтиль    | 72°  | требует n=5 или 10 | {5/2} |
| Оппозиция   | 180° | 6            | {12/6}    |

Несколько решёток накладываются с весами от фактической суммарной силы аспекта в карте. На выходе плотная мандала, читается как «герб момента».

**Сильные стороны**: компактный код, всегда читаемая графика, естественно превращается в иконку или картинку-шапку для бота.

### 1.2. Замощения по доминантному аспекту

Считаем по карте, какой тип аспекта сейчас вносит наибольший вклад (сумма `strength × dignity`), и от этого выбираем тип регулярного замощения плоскости:

- секстиль (60°) → гексагональная решётка
- квадратура (90°) → квадратная клетчатая
- трин (120°) → треугольная
- сильные квинтили (72°) → апериодическое замощение Пенроуза P3
- смешанная картина → квазикристалл по 5-кратной или 12-кратной симметрии

Регионы окрашиваются палитрой планет, чьи аспекты держат сцену. Картинка дня меняется качественно при смене аспектного баланса.

**Сильные стороны**: даёт принципиально разный визуал в разные дни. Хорошо ложится в фон карточки или wallpaper.

### 1.3. «Цветок жизни» из планет

Каждая планета задаёт центр круга, радиус берётся из орба или скорости (медленные планеты — крупнее). Пересекаются только круги планет, между которыми есть аспект, расстояние центров подбирается из соотношения углов так, чтобы получались узнаваемые линзы:

- соединение → vesica piscis (две идентичные дуги)
- секстиль → тройная розетка
- квадрат → пересечение под 90°, читается как «крест»
- трин → классическая «триквета» из трёх линз

Линзы и розетки красятся по природе аспекта.

**Сильные стороны**: каноническая «сакральная геометрия» с прозрачной семантикой. Хорошо смотрится в крупном формате.

### 1.4. Гармонограф / Лиссажу

Пара планет в аспекте кодируется соотношением частот:

| Аспект     | Соотношение |
|------------|-------------|
| Оппозиция  | 1:2         |
| Трин       | 2:3         |
| Квадрат    | 3:4         |
| Квинтиль   | 4:5         |
| Секстиль   | 5:6         |

Сумма таких пар с затуханием рисует одну кривую. Фаза кривой привязывается к текущему моменту, что даёт естественную анимацию.

**Сильные стороны**: единственное семейство, которое осмысленно анимировать. Графика «звучит» — соотношения те же, что у музыкальных интервалов.

### 1.5. Воронои/Делоне по планетам

10 планет плюс узлы как центры на эклиптике (или на плоскости с проекцией от хорошего отображения), вес ячейки складывается из достоинства планеты и силы её активных аспектов. Получается сотовый узор, регионы подкрашиваются палитрой планеты-хозяина.

**Сильные стороны**: даёт нерегулярный, но структурный фон. Хорошо как градиент под текст карточки.

### 1.6. Заливка аспектного поля на колесе

На существующем биуиле проводим аспектные хорды, находим точки их пересечения, заливаем замкнутые области цветом из ruler-шипа знаков, через которые проходят хорды. Минимальная доработка существующего `ZodiacWheel`.

**Сильные стороны**: самое дешёвое расширение, садится поверх уже работающего компонента. Хорошо как «proof of concept» — проверяет, читается ли геометрия момента вообще.

## Часть 2. Модуль-генератор как веб-библиотека

### 2.1. Цели

- Использование вне основного проекта: отдельный npm-пакет, который можно подключить в любое веб-приложение
- Framework-agnostic core: чистый TypeScript, без жёстких зависимостей от React/Vue/Svelte
- Несколько таргетов рендеринга: SVG (как строка и как DOM), Canvas 2D, в перспективе WebGL
- Детерминированный вывод: при одинаковом входе и сидe результат идентичен
- Tree-shakable: каждое семейство паттернов — отдельная точка входа
- Минимум зависимостей: ноль обязательных peer-deps, всё работает в браузере и в Node

### 2.2. Расположение в репозитории

Новый workspace `packages/aspect-patterns/`. Это требует добавить `packages/*` в `workspaces` корневого `package.json`. Альтернатива — `pattern-gen/` рядом с `shared/`, но `packages/` лучше масштабируется, если потом захочется выпустить ещё библиотеки (например, отдельно ephemeris-клиент).

```
packages/aspect-patterns/
  src/
    types.ts              // публичные типы: PlanetPosition, Aspect, Scene, Primitive
    scene.ts              // сцен-граф: примитивы и стили
    palette/
      default.ts          // дефолтная палитра по планетам и аспектам
      tokens.ts           // адаптер для CSS custom properties (--ag-day-*)
    patterns/
      starPolygon.ts      // 1.1
      tiling.ts           // 1.2
      flowerOfLife.ts     // 1.3
      harmonograph.ts     // 1.4
      voronoi.ts          // 1.5
      aspectField.ts      // 1.6
    render/
      svg.ts              // Scene → SVG string / DOM
      canvas.ts           // Scene → CanvasRenderingContext2D
    index.ts              // re-export
  examples/               // мини-Vite-плейграунд
  package.json
  tsconfig.json
  README.md
```

### 2.3. Публичный API (черновик)

```ts
// Вход: подмножество того, что уже считает бэкенд
export interface PlanetPosition {
  id: 'sun'|'moon'|'mercury'|'venus'|'mars'|'jupiter'|'saturn'|'uranus'|'neptune'|'pluto'|'northNode'|'southNode'|string;
  longitude: number;     // 0..360, эклиптическая долгота
  speed?: number;        // градусы/сутки, для радиуса в flowerOfLife
  dignity?: number;      // 0..1, для весов
}

export interface Aspect {
  from: string;          // PlanetPosition.id
  to: string;
  angle: 0|30|45|60|72|90|120|135|144|150|180; // точный угол аспекта
  orb: number;           // фактическое отклонение в градусах
  strength?: number;     // 0..1, нормированный вес
}

export interface PatternInput {
  planets: PlanetPosition[];
  aspects: Aspect[];
  palette?: Palette;     // если не задана — берётся дефолтная
}

export interface RenderOptions {
  width: number;
  height: number;
  background?: string | null;
  seed?: number;         // для любых решений со псевдослучайностью
}

// Каждый паттерн = чистая функция (input, opts) → Scene
export interface Scene {
  width: number;
  height: number;
  primitives: Primitive[];
  meta?: Record<string, unknown>;
}

export type Primitive =
  | { kind: 'circle';  cx: number; cy: number; r: number;  style: Style }
  | { kind: 'arc';     cx: number; cy: number; r: number;  a0: number; a1: number; style: Style }
  | { kind: 'line';    x1: number; y1: number; x2: number; y2: number; style: Style }
  | { kind: 'polygon'; points: [number, number][]; style: Style }
  | { kind: 'path';    d: string; style: Style }; // SVG path data для сложных кривых

export interface Style {
  fill?: string | null;
  stroke?: string | null;
  strokeWidth?: number;
  opacity?: number;
  blend?: 'normal'|'multiply'|'screen'|'overlay';
}

// Высокоуровневый API
export function generate(
  kind: 'star-polygon'|'tiling'|'flower-of-life'|'harmonograph'|'voronoi'|'aspect-field',
  input: PatternInput,
  opts: RenderOptions,
): Scene;

// Рендереры
export function toSVG(scene: Scene): string;
export function toSVGElement(scene: Scene): SVGSVGElement;
export function toCanvas(scene: Scene, ctx: CanvasRenderingContext2D): void;

// Per-pattern named exports для tree-shaking
export { starPolygon } from './patterns/starPolygon';
export { tiling } from './patterns/tiling';
// ...
```

Развязка «pattern → scene» и «scene → render» даёт две выгоды: тестировать паттерны можно без DOM, а рендерер для WebGL/PDF добавляется без правок в логике паттернов.

### 2.4. Палитра и интеграция с дизайн-токенами

Дефолтная палитра содержит цвета по планетам и по семействам аспектов. Через адаптер `tokens.ts` библиотека читает CSS custom properties вида `--ag-day-sun`, `--ag-day-aspect-trine` из браузерного контекста, если они заданы. Это согласует генератор с проектной системой токенов и работает прозрачно, если потребитель пакета определит свои переменные.

### 2.5. Дополнительный слой: Web Component

Поверх core-API имеет смысл собрать `<aspect-pattern>` web-component:

```html
<aspect-pattern
  kind="star-polygon"
  input='{"planets":[...],"aspects":[...]}'
  width="512" height="512">
</aspect-pattern>
```

Это даёт мгновенную интеграцию в любой стек без npm-зависимости от React или Vue, и в самой основной фронтенд-аппе можно использовать его наряду с React-компонентами.

### 2.6. Сборка и публикация

- Сборщик: `tsup` (ESM + CJS + d.ts из одной команды, минимум конфига)
- Цели: ESM как основной выход, CJS для совместимости с Node, IIFE-bundle для CDN
- Размер: цель < 30 КБ minified+gzipped для всего пакета, < 8 КБ на одно семейство при tree-shaking
- Тесты: vitest + snapshot-тесты SVG-вывода + property-тесты на детерминизм при одинаковом входе
- Документация: TypeDoc + Storybook (или Ladle, легче) с живыми ползунками по входным параметрам
- Публикация: на старте под scope `@adaptive-astro/aspect-patterns`, либо нейтральное `astro-aspect-patterns` если планируется отдать в open source независимо от основного проекта

### 2.7. Связь с основным проектом

Бэкенд уже считает позиции планет и аспекты в `backend/src/services/`. Внутри основного фронтенда библиотека подключается обычным `import` и принимает структуры, которые уже идут с API (возможно, с тонким маппером в `frontend/src/lib/patterns/`). Бот на сервере может через node-API вызвать `toSVG(generate(...))`, отрендерить картинку через `resvg-js` (Node-friendly SVG → PNG) и приложить к сообщению.

## Часть 4. Возможные пути развития: представление аспект-графа в 3D

Аспект-граф (вершины — планеты, рёбра — аспекты) сейчас живёт в 2D на круге. Естественная следующая ось развития — поднять его в 3D и получить многогранник. Способы перечислены ниже по убыванию «честности» геометрии и упорядочены так, чтобы было видно, какие можно попробовать на текущей фазе библиотеки, а какие требуют отдельной математической инфраструктуры.

### 4.1. Реальная небесная сфера (физический лифт)

У каждой планеты есть эклиптическая долгота (то, что уже на входе) и склонение или эклиптическая широта (нужно добавить во вход). Точки кладутся прямо на единичную сферу по этим координатам, рёбра аспектов рисуются хордами или дугами большого круга. Convex hull даёт многогранник, в вершинах которого реальные положения планет.

Свойства:
- Геометрически честно: расстояния на сфере соответствуют реальным угловым разностям
- Многогранник нерегулярный, при близких планетах вырождается
- Требует расширить `PlanetPosition` полем `declination` или `latitude`

Кандидат на первый прототип «честного 3D», если хочется именно небо.

### 4.2. Подъём планарного графа (Steinitz + Maxwell–Cremona)

По теореме Штейница, любой 3-связный планарный граф реализуется как 1-скелет выпуклого многогранника. Алгоритм:

1. Проверить 3-связность аспект-графа (большинство содержательных конфигураций 2-связные, нужна аккуратная предобработка, например добавление центра карты как фиктивной вершины со связями ко всем планетам).
2. Tutte-эмбеддинг: фиксируем грань-внешний цикл на выпуклом многоугольнике, остальные вершины как центры масс соседей. Линейная система, единственное решение.
3. Maxwell–Cremona лифт: каждой грани сопоставляется высота через «equilibrium stress», поднимаем вершины в 3D.

Свойства:
- Многогранник «канонический» для данной комбинаторики
- Не зависит от реальных координат планет, только от того, кто с кем в аспекте
- Реализация: нужно решать линейные системы, разумно подключить `numeric.js` или написать SVD/CG руками для 12 вершин

Кандидат на «математически правильный» 3D-режим.

### 4.3. Канонический полиэдр Кёбе–Андреева–Тёрстона (упаковка кругами)

Тот же класс графов (планарных 3-связных) имеет, с точностью до преобразования Мёбиуса, единственную упаковку касающимися кругами на сфере. Центры кругов задают вершины многогранника с midsphere, касающейся всех рёбер.

Свойства:
- Эстетически наиболее «гармоничная» реализация: все рёбра касаются одной сферы, многогранник смотрится сбалансированно
- Алгоритм требует итеративного решателя (метод CirclePack или дискретного потока Риччи)
- Существуют open-source реализации (Stephenson, CirclePack), но Си-зависимости тяжёлые; чистый JS-вариант пишется на пару сотен строк

Кандидат на «красивый» 3D-режим. Дороже по реализации, чем 4.2.

### 4.4. Параболический лифт

Точки на круге `(x, y)` поднимаются в `(x, y, x² + y²)`. Нижняя огибающая выпуклой оболочки соответствует триангуляции Делоне на круге. Топология рёбер автоматически не совпадёт с аспектами, но через выбор `z = f(orb, strength, dignity)` можно добиться того, чтобы выпуклая оболочка включала именно нужные грани.

Свойства:
- Самый дешёвый способ: convex hull в 3D работает за `O(n log n)` и есть готовый библиотечный код
- Гибкий, но в итоге это не «честный» аспект-многогранник, а декоративное возвышение
- Хорош как переходный шаг, чтобы научиться отдавать сцену 3D-рендеру

### 4.5. Подмена симметричной конфигурации классическим многогранником

Если детектор аспектных конфигураций (`aspectClassifier.ts`) опознал «грандиозный паттерн», его сразу заменяем на каноническое тело:

| Паттерн                       | Многогранник                  |
|-------------------------------|-------------------------------|
| Большой трин (3 точки 120°)   | Тетраэдр (3 планеты + центр)  |
| Тау-квадрат                    | Квадратная пирамида            |
| Большой крест                  | Октаэдр                        |
| Йод                            | Треугольная пирамида           |
| Мистический прямоугольник      | Бипирамида                     |
| Звезда Давида / большой секстиль | Октаэдр или антипризма        |
| Полный набор аспектов на 12 точках зодиака | Икосаэдр / кубооктаэдр |

Свойства:
- Реализация почти бесплатная: каждое тело — статическая модель, выбор по результату классификатора
- Читается интуитивно, особенно хорошо для иконок и шапок
- Не работает на «несимметричных» картах: туда отдаётся один из общих методов 4.1–4.3

### 4.6. Force-directed на сфере

Spring layout в 3D с пружинами по рёбрам аспектов. Длина пружины пропорциональна углу аспекта (60 → 1, 90 → 1.5, 120 → 2, 180 → 3 в условных единицах), вершины удерживаются на единичной сфере штрафным членом или нормированием на каждом шаге.

Свойства:
- Не каноничный, зато естественно анимируется
- Хорошо ложится на Three.js, играет с интерактивом (можно тянуть планеты мышью)
- Геометрия не уникальна, зависит от начальных условий

### 4.7. Двойственный по Вороному на сфере

Строим сферическую диаграмму Вороного по планетам, её двойственный — сферическая триангуляция Делоне. Грани становятся «зонами влияния планет», рёбра соединяют планеты-соседей по доминированию.

Свойства:
- Естественно отдаёт заливку граней в цвета планет-хозяев
- Геодезические алгоритмы сложнее плоских, но есть библиотеки (`d3-geo-voronoi`)
- Может комбинироваться с 4.1: те же сферические координаты служат входом

### 4.8. Экструзия по времени

Третья координата — время. Долгота планеты меняется со временем, аспект-граф протягивается в призматическую структуру. На каждом срезе плоский граф, между срезами — поверхности, где аспект «закрывается» (орб минимален).

Свойства:
- Уникальный угол: показывает не текущий момент, а окно вокруг него
- Тяжёлый для рендера: нужна сегментация по времени и поверхности
- Пересекается с тем, что уже считает бэкенд для V2 timing'a, поэтому может переиспользовать данные

### 4.9. Что брать на текущей фазе

Приоритеты с точки зрения «дёшево попробовать, увидеть, есть ли смысл»:

1. **Способ 4.2 (Tutte + Maxwell–Cremona)** — математически чистый, не требует расширения входа, реализуется в пакете на чистом TS. Хорошо ложится на отдельный экспорт `toPolytope(scene) → 3D mesh`.
2. **Способ 4.3 (Koebe canonical)** — следующий шаг, если 4.2 заработает и захочется красивее. Дороже по математике, требует итеративного решателя.
3. **Способ 4.1 (небесная сфера)** — параллельная ветка. Полезен, если в команде уже есть склонения планет на бэкенде; иначе сначала добавить их в API. Картинка «честнее», но визуально менее предсказуемая.

Способ 4.5 (классические тела по конфигурациям) живёт независимо и хорошо комбинируется с любым из 4.1–4.3 как «fast path» для симметричных карт.

### 4.10. Что нужно добавить в пакете

- Новый таргет рендера: `toThree(scene3D): THREE.Object3D` или нейтральный `Mesh { vertices, faces, edges }`, чтобы потребитель сам подключал свой 3D-движок
- Расширить `Scene` опциональным `Scene3D { vertices: Vec3[]; faces: number[][]; edges: [number, number][] }`, чтобы не ломать существующее 2D-API
- Solver для подъёма (Tutte + Maxwell–Cremona) вынести в отдельный модуль `geometry3d/`, тестировать на эталонных графах (куб, октаэдр, призма) до интеграции с реальными аспектами
- В playground добавить переключатель `2D / 3D` и базовую Three.js-сцену, чтобы видеть результат

Эта часть остаётся в roadmap как «следующая большая ветка после Фазы 6», но не блокирует более дешёвые 2D-семейства.
